# Quickstart: Validate Complete Parity Work

This guide is for an isolated, authorized test environment. It does not assert that any feature is implemented.

1. Record the installed reference version with `claude --version` and nox/Pi revisions. Record platform and availability conditions in the [inventory](contracts/inventory.md).
2. Reconcile every page in the current [documentation index](https://code.claude.com/docs/llms.txt), the installed command tree, and candidates in the older [restored source map](https://github.com/ChinaSiro/claude-code-sourcemap/tree/main/restored-src) into the [inventory](contracts/inventory.md). The source map may be read remotely for discovery; do not clone it or copy its code into nox. Use current documentation and installed behavior to establish each contract.
3. Create a disposable repository and matched settings for the reference and nox. Capture the initial files and session state. Use nox-native names for nox configuration.
4. Define normal, denied or failing, persistence, and interaction cases under [observable behavior](contracts/observable-behavior.md). For external input, add malformed and unauthorized cases with synthetic sensitive values, the expected validation and permission decisions, the protected side effect, and prohibited disclosures. Declare any nondeterministic normalization before running them.
5. Run safe local reference probes and nox probes with the same inputs. Preserve raw output and side-effect records. Account- or service-gated behavior stays open until authorized access permits observation; do not substitute guessed results.
6. Compare behavior and Pi terminal states. Capture unrelated Pi functional workflows before affected source changes and compare them after each slice. Record each mismatch as a discrepancy; mark the inventory item `verified` only when all applicable cases pass.
7. Before each code change, run a focused behavior test and confirm that it fails for the expected reason. Make the smallest change that passes it, then run relevant unit, integration, and end-to-end checks, `npm run check`, the Pi functional regression matrix, and a project coverage report. Application work cannot be called complete until aggregate lines, statements, functions, and branches each reach 80%; a zero-denominator or unmeasured metric fails. Review the diff for credentials, input validation, authorization, applicable injection and request-forgery defenses, rate limits, and data leaks. Use isolated fixtures and no paid provider calls for routine tests.
8. Before an unqualified complete-parity claim, refresh the reference version, reconcile every inventory source, and require every inventoried item to pass with zero `discrepant` and zero `gated-unverified` items.

The aggregate project coverage command has not yet been added. Until task execution creates and validates it, step 7's 80% gate is unmeasured and application completion cannot be asserted.
